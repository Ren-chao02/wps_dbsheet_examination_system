# 客观题 + 知识点抽题组卷 + 批改存档 设计方案

> 2026-10-11 定稿（需求已与项目负责人逐条确认）。系统要落地到校园网、几千名学生规模。

## 一、目标与已确认的决策

| # | 决策点 | 选定方案 | 备注 |
|---|--------|----------|------|
| 1 | 每生题目不同的程度 | **同构替换** | 每人卷子的总分、知识点覆盖、难度分布完全一致，只有题目不同；成绩可直接比较 |
| 2 | 知识点体系 | **复用现有 66 项能力点** | 题目落库 `capabilityIds`；不新建知识点树 |
| 3 | 组卷形态 | **固定题位 + 抽题规则混合** | 每个题位要么钉死某道题，要么声明"从某能力点×难度池抽 1 道" |
| 4 | 客观题题型 | **单选 + 多选 + 判断** | 三种都可 100% 确定性判分；填空/简答暂不做 |
| 5 | 批改存档范围 | **完整留痕 + 可导出** | 规则版本快照 + 人工复核留痕 + 按考试/批次导出 |

## 二、一条必须先满足的硬约束（否则功能上线即事故）

**同一题位内的候选题，其引用的表名 + 字段名集合必须完全一致。**

原因：实操题的题面会写"在「员工信息表」中把「入职日期」改为日期格式"。若同一题位下的变体题引用了不同的表/字段，学生打开自己被分配的那份表格就找不到对应的表，题目无从作答。

落地方式：
- 题目增加显式声明字段 `schemaRefs`（表名数组 + 字段名数组），出题时由骨架生成器自动带出、教师可核对；
- 组卷时做校验：同一题位候选池内 `schemaRefs` 不一致的题不允许同池，给出明确报错；
- 校验不过 = 该题位候选不足，按第 5 条的降级规则处理。

## 三、数据模型（增量，不动存量数据）

```
Question
  + capabilityIds  String[]    // 能力点 id（知识点），落库后才有"按知识点抽题"
  + objectiveAnswer Json?      // 客观题答案：{ options: [{key,text}], correct: string[] }
  + schemaRefs     Json?       // 实操题引用的表名/字段名（题池等值校验用）
  + version        Int @default(1)  // 规则变更时自增，供判分快照引用

enum QuestionType
  + single_choice | multiple_choice | true_false   // 与现有 5 种实操题型并存

PaperQuestion                                   // 题位
  + slotType  String @default("fixed")          // fixed | rule
  + rule      Json?                             // rule 题位：{ domain, capabilityIds[], difficulty, score, count }

StudentExamQuestion                             // 新表：每生卷子快照
  examId, studentId, slotIndex, questionId, score, sortOrder, source(fixed|rule)
  @@unique([examId, studentId, slotIndex])      // 幂等/并发安全

GradeReviewLog                                  // 新表：人工复核留痕
  submissionDetailId, submissionId, reviewerId, beforeScore, afterScore, reason, createdAt

SubmissionDetail
  + gradedWith Json?    // 判分时的快照：{ questionVersion, rules: [...], gradedAt }
```

## 四、模块改动

### 1. 出题端
- 题库支持客观题编辑（题干 / 选项 / 正确答案 / 解析 / 能力点）；
- 实操题编辑页增加"引用声明"（表名、字段名），默认从骨架生成器带出。

### 2. 组卷端
- 试卷编辑器支持两类题位；固定题位保持现有交互不变；
- 新增"按知识点分配"面板：选能力点 → 定题数 / 分值 / 难度 → **实时显示候选池大小**；
- **候选题只有 1 道时明确警告**（否则"每生不同"会静默退化成"全员同题"，教师毫不知情）。

### 3. 开考端

`POST /api/my-exams/:id/start-wps` 生成该生卷子快照（幂等，靠唯一约束），同时提供考前批量预生成接口，把 3000 人的生成压力从开考瞬间挪到开考前。

### 4. 判分端

判分入口按题型分流：

```
gradeQuestion(question, submission)
  ├─ 客观题 → objective-grader.ts（确定性比对，交卷即出分）
  └─ 实操题 → 现有 rule-engine（教师触发自动阅卷）
```

客观题判分不触碰规则引擎，规则引擎一行不改。

### 5. 存档端

- 判分时把"当时用的规则 + 题目版本"写进 `SubmissionDetail.gradedWith`；
- 人工改分写 `GradeReviewLog`（谁 / 何时 / 原分 → 新分 / 理由）；
- 导出中心新增"含判分明细 + 复核记录"模板，按考试或批次导出 Excel 归档。

### 6. 学生端
左侧题目区按题型渲染：客观题给选项控件（单选 radio / 多选 checkbox / 判断 radio）、切换题目时保留已选、交卷时随 `answers` 一并提交；实操题显示"请在右侧表格中完成"。

## 五、边界与降级规则（已确认）

| 场景 | 规则 |
|------|------|
| 纯客观题考试 | 不分配 WPS 表格、环境检测不出现 WPS 登录项（现有逻辑按"有无分配表"判断，天然成立） |
| 随到随考 / 迟到入场 | 开考时生成快照，天然覆盖 |
| 题库中途变更 | 快照已落库，不受影响；题目编辑另加"进行中的考试引用时禁止修改"的守卫 |
| **候选题不足** | **警告但允许开考**：该题位退化为"全员同一题"，并在开考确认页汇总列出受影响的题位 |
| 卷子锁定 | 提供"考前锁定卷子"开关：锁定后题库变更不影响已生成快照（快照本身已保证，锁定是给教师的心理可见性） |

## 六、分期

1. **第一期：客观题**（题型 + 判分器 + 学生作答 + 教师出题）——独立可交付；
2. **第二期：知识点抽题组卷 + 每生卷子快照**（含 schemaRefs 校验与候选题预览）——核心，改动最大；
3. **第三期：批改存档与导出归档**。

第二期完成时"客观题 + 实操题混合组卷"自动成立。

## 七、验收要点

- 同一场考试任意两名学生的卷子：总分相同、能力点覆盖相同、难度分布相同、题目至少一处不同；
- 每个学生的卷子快照可查（教师端能看到"他当时做的是哪套题"）；
- 候选题不足时开考前有明确警告，不出现"静默全员同题"；
- 题库改题后重判历史答卷，判分结果仍按当时的规则复现；
- 人工改分可追溯到人、到时间、到理由。
