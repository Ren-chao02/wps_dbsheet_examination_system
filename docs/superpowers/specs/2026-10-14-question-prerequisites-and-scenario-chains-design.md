# 题目前置契约 + 场景链设计方案（练习成链 / 考试自包含）

> 2026-10-14 定稿（五个关键取舍已与项目负责人逐项确认）。落地场景：校园网、几千名学生规模的真实使用。

## 一、问题：题面假定了一个系统从不保证的初始状态

典型症状（项目负责人 2026-10-14 提出）：题库里有「在「员工信息表」中新建一个时间字段命名为'打卡时间'…」这样的题。如果前面没有铺垫，学生的表格里根本没有「员工信息表」——学生打开表格不知道是自己错了、进错考场了，还是题目出错了。

这类题不是个别现象：51 道实操题里有一条 20 题的「员工信息表」累积链（第 1 题建表 → 依次加字段 → 再做视图/筛选/排序/分组），后面 19 题全部建立在前面产物之上；另有项目/任务、销售、看板等若干条同类线。

### 现状机制（2026-10-14 逐条核实）

| 环节 | 现状 | 证据 |
| --- | --- | --- |
| 学生的表格从哪来 | 系统**从不复制、从不新建**表格。学生操作的是教师在 WPS 里手工准备的真实文件，系统只登记 `fileId` + 分享链接 + 快照 token | `routes/exam-table-assignments.ts:21-31`、`prisma/schema.prisma:1119-1151` |
| 考试开考 | 对表格**零操作**（不改、不建、不清） | `routes/my-exams.ts:382-644`（无任何写操作） |
| 练习开练 | `resetFile()` 把该文件**所有 sheet 删光** → 学生总是从空表开始 | `routes/practice.ts:228`、`engine/adapters/kingsoft-adapter.ts:549-571` |
| 教师端引导 | 「请先在 WPS 中为每个考生创建**空白**多维表格」 | `pages/teacher/ExamConfigWizard/WpsTableAssignStep.tsx:270` |
| 判分定位方式 | 按规则参数里的**表名/字段名**精确匹配 | `engine/rule-engine.ts:250-259` |
| 缺表时的判分 | 对应规则 `passed:false` + `errorMessage:「未找到表「X」」`，`needsReview:false` —— **无声地判不通过**，学生只看到红叉 | `engine/rule-engine.ts:295-305` 等约 30 处 |
| `schemaRefs`（引用声明） | 存在但**形同虚设**：只能教师手填、组卷 UI 不可编辑、服务端不继承题目级声明、抽题是 strict→放宽 的**软**约束，题位规则没写时完全不校验 | `QuestionEditor.tsx:558-593`、`utils/paperAssembly.ts:43-44`、`routes/papers.ts:280-289`、`services/paper-generator.ts:216-239` |
| 题库数据 | 51 道实操题 `schema_refs` **全为 NULL**；约 35 道能从 `answer_rules[].params.tableName` 直接读出表名 | 2026-10-14 生产库查询 |

**结论**：教师引导（空白表）与题面假定（表已存在）互相矛盾；而「学生能否完成」完全取决于抽题运气与作答顺序，系统层面既无保证也无提示。

### 学生当前的真实体验

1. 抽到链中间的题 → 打开表格没有题面说的表 → 困惑（不知道该建，还是自己漏做了什么）；
2. 硬着头皮做了 → 判分「未找到表「X」」→ 判不通过，学生无从知道原因；
3. 考试组卷若混入引用不同表结构的同题位变体题 → 部分学生必然做不了（`slot-preview` 有橙警，但依赖的 `schemaRefs` 断链，实际不生效）。

### 关联的已知问题（本次不修，但必须标记）

51 道实操题中有 **16 道题的规则用了引擎未实现的 action**（共 17 个 action 名：「创建空白多维表格并认识基本界面结构」一题用了两个）。涉及 `verify_dashboard_chart`、`verify_kanban_card_config`、`verify_automation_workflow`、`verify_ocr_functionality`、`verify_default_value`、`verify_field_group`、`verify_view_sharing`、`verify_excel_import`、`verify_auto_match`、`verify_hierarchy_structure`、`verify_kanban_drag_operation`、`verify_scheduled_automation`、`verify_ai_field_config`、`verify_interface_elements`、`verify_table_exists`、`verify_line_chart`、`verify_pie_chart`。引擎对未知 action 一律返回 `needsReview:true`（`engine/rule-engine.ts:1689-1703`），练习判分把 needsReview 计入"做错"（`services/practice-grading-service.ts:263-269`）——**这 16 道题目前永远判不出分**。其中有的是 schema 层面本就不可能自动判的（AI 拍照识别、界面认识）。本次只在回填脚本的「待人工确认」清单里标记，并禁止它们进入考试池。

## 二、已确认的决策

| # | 决策点 | 选定方案 | 理由 |
| --- | --- | --- | --- |
| 1 | 这类累积式题的定位 | **练习成链、考试自包含** | 练习按教学顺序成链（忠于原题设计）；考试只收单题自包含版本，改动最小、最稳 |
| 2 | 「链」怎么定义 | **自动推导 + 落在题目字段**（不建 Chain 实体） | 推导数据现成（判分规则里就有表名）；新题入库自动归链，维护成本最低 |
| 3 | 前置条件怎么给学生看 | **结构化前置契约 + 系统渲染**（不改题面正文） | 一份声明同时喂给组卷校验/归链/提示/判分归因；题面保持干净，链内练习不重复啰嗦 |
| 4 | 链内答题顺序 | **建议但不强制** | 判分只看终态，强制顺序既不必要也挡不住学生探索；前置未完成的题给提示即可 |
| 5 | 逐步检查（每题即时判分） | **留二期** | 需在答题中途反复读 WPS schema 并处理"刚建的表服务端还读不到"的时序，MVP 用整卷判分 + 归因 |

**贯穿全局的取舍**：判分逻辑**一行不改**（仍是按名字找表、只看终态），本设计只改「学生知道该做什么」与「组卷保证拿到的题结构一致」。因此即使推导器出错，最坏影响是多显示一条提示，不会污染判分。

## 三、核心概念：前置契约（Prerequisite Contract）

每道实操题声明两件事：

- `requires`：做这题之前必须具备什么（表 / 表+字段 / 表+视图）
- `creates`：做完这题会得到什么（表 / 字段 / 视图）

### 推导规则（`answerRules[].action` → 语义）

引擎现有 29 个处理器的语义是稳定的，可直接映射：

| 规则动作（节选，完整映射表在代码里） | 推出的语义 |
| --- | --- |
| `check_table_exists` / `check_table_name` / `check_table_count` / `check_table_fields`(T) | **creates** 表 T（考点就是"把这张表建出来/建对"） |
| `check_field*`(T,F)（exists/type/format/options/required/unique/formula/default/link_*） | **requires** 表 T；**creates** 字段 T.F |
| `check_view_exists`(T,V) | **requires** 表 T；**creates** 视图 T.V |
| `check_view_filter / sort / group / field_hidden / type`(T,V) | **requires** 表 T **和视图 T.V**（视图是前序题的产物） |
| `check_record_*`(T) | **requires** 表 T（且表中要有记录） |
| `check_form_*`(T) | **requires** 表 T；**creates** 表单 T.表单 |
| 未知 action（引擎未实现） | 推导不出 → 进「待人工确认」清单，且标记为"不可自动判分" |

参数键沿用现有约定：`params.tableName / fieldName / viewName`。

### 用途（一份声明，四个消费方）

1. **学生提示**（考试答题页）：渲染「本题需要什么」提示条；
2. **练习归链**：同一场景的题按 `scenarioOrder` 组成链；
3. **组卷等值校验**：同题位候选题的"涉及的表集合"必须一致（修复现有断链）；
4. **判分归因**：多题因同一缺失失败时，聚合为一条链级原因。

### 等值签名（组卷用）

等值签名 = `requires.tables ∪ creates.tables`（升序、去重、`|` 拼接），与现有 `schemaRefsSignature` 语义兼容（`services/paper-generator.ts:60-67`）。旧数据 `{tables, fields}` 读入时：`tables` 直接作为"涉及的表"参与签名，`requires`/`creates` 留空等待推导器补全——**不猜语义**。

## 四、数据模型（增量）

```
Question
  + scenario       String?   // 场景名（初始 = 主表名，如「员工信息表」；教师可改）
  + scenarioOrder  Int?      // 场景内序号（由拓扑排序预填，教师可改）

  schemaRefs Json?  // 结构扩展（向后兼容，读时归一化）：
                    // {
                    //   requires: { tables: string[], fields: {table,field}[], views: {table,view}[] },
                    //   creates:  { tables: string[], fields: {table,field}[], views: {table,view}[] },
                    //   tables:   string[],   // 旧字段：涉及的表（= 等值签名依据）
                    //   fields:   string[]    // 旧字段：涉及的字段名
                    // }
```

- 全部为可空列，**不要求一次性迁移**；未填的题行为与今天完全一致。
- 场景名初始取"该链根题创建的主表"（如「员工信息表」），教师可改成人话（「HR 员工档案实战」）。

## 五、自动推导、聚类与存量回填

### 1. 推导器（纯函数，`engine/prerequisite-deriver.ts`）

输入：题目的 `answerRules`（可选加题面文本做兜底）；输出：`{ requires, creates }`。

- 按第三节的映射表逐条规则归并；
- 同一题里"既 requires 又 creates 同一张表"时（如先建表再在表上建字段），合并为 creates（本题自给自足）；
- 推导不出的题（unknown action / 无表名）→ 输出空契约 + `unresolved: true` 标记。

### 2. 归链（`services/scenario-cluster.ts`）

- **根题**：能 `creates` 出表的题；一条链的名字取该链根题创建的主表名。
- **归属**：其余题按 `requires` 归到对应链；无 requires 但有题面线索的进人工清单。
- **跨链题**（同时 requires 两条链的表，例如「设置关联字段允许多条记录关联」同时用到 任务表 + 员工信息表）：**不自动猜**，进「待确认清单」，由教师在题库里指定 `scenario`。
- **排序**：链内拓扑排序（`creates(A) ∩ requires(B) ≠ ∅ ⇒ A 排在 B 前`）；无依赖关系的按二级分类现有顺序；环形依赖退化为按分类顺序并进待确认清单。

### 3. 回填脚本（`packages/server/scripts/backfill-question-refs.ts`）

- **幂等**：默认只填 `scenario` 为空的题；`--force` 才覆盖已有值（供日后重跑）。
- 跑完导出两份清单（Markdown/CSV）：
  - 「自动填充完成」——可直接用；
  - 「待人工确认」——推导不出 / 跨链 / 环形依赖 / 规则动作未实现（第四节末那段，额外标 `ungradeable`）。
- 注意：`packages/server/scripts/` 是 gitignore 白名单，要入库需先加 `!` 规则。
- 推断出的场景归属同时写进 `prisma/seed-data/question_bank_wps_multidimensional_table.json`，保证重建库时一致。

### 4. 预估产出（以脚本实跑为准）

| 场景（预估） | 题数（预估） | 说明 |
| --- | --- | --- |
| 员工信息表 | ~19（+2 待人工） | 链本体 19 道能推导；「为文本字段设置默认值」「使用字段编组批量管理字段」题面也指向这张表，但规则未实现，需人工归链或先修规则 |
| 项目表 + 任务表 | ~4 | 另有跨链题待人工指定 |
| 看板（任务管理表） | 3 | 其中 2 道规则未实现 |

| AI 助手 | 2-3 | 全部规则未实现 |
| 自动化工作流 | 2 | 全部规则未实现 |
| 销售报表 | 2 | — |
| 其余单题场景 | 若干 | 学生表+课程表、联系人表、订单管理表、设备巡检表、项目立项表、CRM 综合等 |

## 六、练习侧：成链

### 入口（PracticeList）

- 现有「按分类/难度自由抽题」入口**保留不动**；上方新增**「场景实战」卡片区**：每场景一张卡（场景名、题数、总分、进度徽标：未开始 / 进行中 3/20 / 已完成 88 分）。
- 新接口 `GET /practice/scenarios`：返回当前学生可见的场景列表 + 该生每场景最近一次记录（进度/得分）。
- **只有题数 ≥ 2 的场景出卡片**；单题场景并入自由练习（不出现"1 题的场景实战"）。

### 开练

`POST /practice/start` 新增 `scenarioKey` 参数（与 `questionIds`、分类/难度参数互斥）：

1. 取该场景全部 published 题，按 `scenarioOrder` 排序（**不随机**）；
2. `resetFile()` 清空表格 → 建 `PracticeRecord`（题目快照落进现有 `questions` JSON，附 `scenarioKey`）；
3. 场景题数**不受现有 20 题上限约束**（放宽到 50；超过 50 直接拒绝并提示，不静默截断）。

### 断点续做（本次练习侧最实质的改动）

现状两个硬伤：题目快照只存在浏览器路由 state（刷新即丢）；每次开练都 resetFile + 删除遗留的 in_progress 记录（`routes/practice.ts:249-254`）。单题练习尚可忍受，一条 20 题的链做到第 9 题被打断就等于前 8 题全废。

- 学生进练习页时若存在**自己进行中的场景记录** → 顶部提示「上次的『员工信息表实战』做到第 3/20 步，[继续] [重新开始]」；继续 = 不重置表格，直接回到该记录。
- 新接口 `GET /practice/records/:id`：返回题目快照 + shareUrl，供刷新/直接进 URL 时恢复；前端当前步骤存 localStorage（`practice_step:<recordId>`）。
- **约束：同一个练习文件同一时刻只能有一条进行中的链**（这是现状 resetFile 语义的必然推论，只是第一次明确告诉学生）：开另一条链前提示「开始新的实战会清空当前表格，未完成的『员工信息表实战』将中断」。

### 顺序与提示

- 链内**建议顺序、不强制**：答题卡照旧可跳题；前置未完成的题在答题卡上标灰点 +「前置未做完，这题可能做不了」。
- 链内**不显示**考试那套前置提示条（上方已有进度与顺序，提示反而是噪音）。

### 判分与归因

- 判分链路不变（提交整卷、同步判分、复用 `gradePracticeRecord`）。
- 结果页按链顺序展示，加两层归因：
  - **单题**：把规则 `errorMessage`（「未找到表「X」」）翻成学生能懂的话——「你的表格里没有『员工信息表』这张表，本题要求在这张表上操作」；
  - **链级**：多题因同一缺失失败时折叠成一条——「第 3 步没建『员工信息表』，导致第 4–6 步连带失败」，而不是给学生看 6 条红叉。
- 顺手区分 `needsReview`：结果页把「待人工复核」与「做错」分开显示（今天两者在学生端长得一样）。

## 七、考试侧：自包含

核心认识：判分只看终态、按表名找表——学生自己建的「员工信息表」和老师预置的在判分眼里**没有区别**。所以自包含不需要系统建表，只需要把"你可以自己建"这件事告诉学生：学生现在困惑的不是「不会建」，是**不敢建/不知道该建**。

### 1. 前置提示条（主要改动）

- 数据：`toStudentQuestion`（`routes/my-exams.ts:151-174`）现在把 `schemaRefs` 剥掉了，改为下发**归一化后的 `requires`**——只含表名/字段名/视图名，**不含任何答案信息**（`answerRules` 仍不下发）。
- 渲染：题目描述下方一条中性提示条（与现有「操作提示」Alert 并列、样式区分），文案由前置契约生成：

  > 本题需要「员工信息表」（含字段：姓名、入职日期）。**如果你的表格里还没有它，请先在左侧新建这张表并建好这些字段**，再完成题目要求。

- 取舍：**提示条只陈述需要什么，不判断是否已存在**。答题页现在不读 schema；若加判断，每题要多打一次 WPS 接口，还要处理"网页里刚建的表服务端还读不到"的时序。二期若要「✓ 已就绪」徽标，复用独立窗口模式下 `WpsLivePreview` 的读表通道。
- `requires.tables` 为空的题不显示提示条。

### 2. 组卷断链接上（不改则"每生一份等值卷子"一直是假的）

- **固定题位**：`PUT /api/papers/:id/questions` 落库时，题位未显式声明 `schemaRefs` 就从 `question.schemaRefs` 继承（`routes/papers.ts:280-289`）。
- **抽题题位**：组卷编辑器把 `schemaRefs` 从「UI 不编辑，仅透传保留」改为**可见可编辑**（`utils/paperAssembly.ts:43-44`）——教师声明「这个题位要在『员工信息表』上考」，`paper-generator` 的 strict 校验才真正生效。
- 接上之后，`slot-preview` 现有的「候选题引用结构不一致」橙警才是真的有意义（`services/paper-generator.ts:286-312`），教师按一个结构准备表格即可。

### 3. 判分呈现（逻辑零改动，只改话术）

学生结果页 / 教师阅卷页把 `errorMessage:「未找到表「X」」` 翻成人话。判分逻辑一行不改。

### 4. 与教师侧引导从此对齐

教师端写着「为每个考生创建**空白**多维表格」，题面过去却假定表已存在；自包含化之后两个说法第一次一致：**空白表 + 题面/提示条告诉你建什么**。

### 5. 不能进考试池的题

- 规则 action 未实现的 16 道（第四节末）；
- 考"说明/理解/界面认识"的题（如「创建时间字段并区分与日期字段的差异」后半句「说明时间字段与日期字段的主要区别」根本无法自动判）；
- 单题场景中依赖前序产物的题。
这些题仍可用于练习（链内），但不进组卷候选池——在题库列表加状态标签，组卷时过滤。

## 八、教师端

1. **题目编辑器：「引用声明」卡片 → 「前置契约」卡片**（现为两个手填 tags Select，`pages/teacher/QuestionEditor.tsx:558-593`）：
   - `requires` / `creates` 两个分组（表/字段/视图）；
   - **「从判分规则自动推导」按钮** → 新接口 `POST /api/questions/derive-refs`，返回推导结果与依据（哪条规则推出什么），教师确认后写回；
   - **学生端提示条预览**（所见即所得，避免文案上线才发现不通顺）；
   - 旧 `{tables, fields}` 作为 fallback 展示，推导成功后以推导结果为准。
2. **题库列表加「场景」列 + 场景筛选**，可分组展示（一条链的题挨在一起、顺序可见）——这是教师核对回填结果的界面。
3. **组卷编辑器**：题位 `schemaRefs` 可见可编辑 + 冲突警告强化（第七节）。

## 九、边界与风险

| 情形 | 处理 |
| --- | --- |
| 推导器出错 | 最坏是多显示/少显示一条提示，**判分与抽题不受影响**（等值签名仍以"涉及的表"为准，人工可改） |
| 学生把表名建错（「员工信息 表」） | 提示条给出了确切表名——这正是不判断"是否已存在"也能救回大部分困惑的原因 |
| 一条链 > 50 题 | 开练直接拒绝并提示，不静默截断 |
| 单题场景 | 不出「场景实战」卡片，并入自由练习 |
| 跨链题 / 环形依赖 / 推导不出 | 一律进「待人工确认」清单，教师指定，不自动猜 |
| 两生共用一张练习表 | 现状已有 UI 警告，本次不变 |
| 场景内题目增删 | `scenarioOrder` 由教师维护；回填脚本 `--force` 可重跑 |

## 十、测试

- **推导器**（`engine/__tests__/prerequisite-deriver.test.ts`）：以真实 51 题的 `answerRules` 做夹具（含推导不出的 16 道），断言 requires/creates 与 unresolved 标记；

## 十二、实施顺序建议（交由 writing-plans 细化）

1. **推导器 + 字段 + 回填脚本**——纯后端纯函数，先跑出真实数据，看清全景（预估场景表）；
2. **教师端前置契约卡片 + 题库场景列**——人可校对数据；
3. **考试侧**：提示条 + 组卷继承（教师按结构准备表格的必要条件）；
4. **练习侧**：场景卡片 + 按链开练 + 断点续做 + 归因（工作量最大的一块）；
5. 测试补齐 + 端到端验收。
