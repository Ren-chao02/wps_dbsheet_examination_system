# 千级开考压测结果（2026-10-23）

> 环境是**开发工作站**（单机、本地 PostgreSQL 15 / Redis 7），结论是基线，不是生产容量承诺。
> 压测服务器从干净 worktree 启动（提交 `ea0c46f`，端口 3010），避免并行会话的未提交改动影响结果。

## 方法与数据

- 隔离数据（可一键清理）：1000 名学生（用户名 `99000001+`）、5 道单选客观题、1 场已发布考试（无批次、无 WPS 表格要求）；所有对象带 `9900*` / `[LOADTEST]` / `LT-` 前缀。
- k6：`SCENARIO=opening`、200 VUs，每人一轮「登录 → 开考 → 取卷 → 5 次自动保存 → 交卷」。
- 发现并修复压测脚本缺陷：
  1. `SCENARIO` 参数此前未生效，opening 与 steady 会**同时**启动（400 VU 混合负载）——已改为只运行指定场景（`3982637`）。
  2. steady 场景按全局迭代序号取学号，第二轮起越界——已改为按 VU id 固定同一学生（`db1e728`）。
  3. 登录失败后毫秒级重试，瞬间打满验证码限流（实测 10 万次/分钟）——已加失败退避（`8b4ed0a`）。
  4. 服务端已改为「答案存服务端、token 为 UUID」，脚本改为优先使用 E2E `debugAnswer`（`f73a474`）；干净服务器以 `E2E_CAPTCHA_DEBUG=true` 启动，且安全修复后仅回环 socket 放行。
- 复现入口：`tests/load/seed-loadtest.ts`、`tests/load/cleanup-loadtest.ts`（均要求 `LT_CONFIRM=yes`，密码从 `LT_PASSWORD` 读取，不写入仓库）。
- 压测数据在结束后已清理，残留计数为 0（users/exams/questions/rooms）。

## 结果六：登录优化后复测（原生 @node-rs/bcrypt + IP 限流 1000）

`bcryptjs`（纯 JS）在 200~300 人同时登录时把 CPU 打满，登录 p95 25~33 秒，并连带拖慢开考/心跳。切换原生 `@node-rs/bcrypt`（哈希格式兼容，存量密码无需重置）后：

**k6 开考 200 VUs（有预生成快照）**：原始数据 `results-2026-10-23/k6-opening-200-nativebcrypt.json`

| 阶段 | 优化前 p95 | 优化后 p95 |
| --- | --- | --- |
| 登录 | 24.91 s | **4.11 s** |
| 开考 | 2.13 s | **0.48 s** |
| 取卷 | 1.18 s | **0.24 s** |
| 自动保存 | 0.76 s | **0.13 s** |
| 交卷 | 0.87 s | **0.04 s** |

- 0 失败，全部阈值通过；迭代 p95 从 41.6 s 降到 19.7 s（其中 15 s 是脚本思考间隔）。

**k6 稳态 300 VUs（60 秒）**：原始数据 `results-2026-10-23/k6-steady-300-nativebcrypt2.json`

| 阶段 | 优化前 p95 | 优化后 p95 |
| --- | --- | --- |
| 登录 | 32.87 s | **5.13 s** |
| 心跳 | 12.19 s | **0.10 s** |
| 自动保存 | 0.69 s | **0.12 s** |

- 0 失败，全部阈值通过。

**同时修复的容量问题**：登录 IP 失败限流默认 100 次/15 分钟，在 300 人同 IP 并发登录时会瞬时触顶（成功请求的计数回退要等响应结束），429 重试又打满验证码限流。账号锁定已防爆破，IP 限流只是兜底，默认已放宽到 1000。

## 结论与建议

1. **P1 预生成有效**：同样 200 人并发，开考 p95 从 7.91 s（现场生成）降到 2.13 s（读预生成快照），约 **3.7 倍**；1000 人预生成只需 2.31 s。登录优化后进一步降到 **0.48 s**。
2. **登录瓶颈已消除**：切换原生 `@node-rs/bcrypt` 后，200 人同时登录 p95 从 24.91 s 降到 4.11 s（300 人稳态 5.13 s），且哈希格式兼容、存量密码无需重置。登录 IP 限流默认从 100 提到 1000，避免整班 NAT 并发被误伤（账号锁定仍防爆破）。
3. **开考（有快照）200 并发 0 失败，p95 0.48 s**；shared advisory lock 没有串行化开考。无快照兜底路径 p95 仍为 7.91 s（固定题位）/ 8.62 s（规则题位），再次说明预生成是千级开考的前提。
4. **稳态 300 人**：0 失败；优化后心跳 p95 0.10 s、自动保存 p95 0.12 s。原 12 s 心跳延迟是 bcryptjs 占满 CPU 导致的连带效应，已随登录优化消失。
5. **规则题位成本**：预生成吞吐从 433 人/秒（固定题位）降到约 135 人/秒；无快照时开考 p95 8.62 s、取卷 p95 5.13 s。预生成仍是千级开考的前提。
6. **本次压测机是开发工作站**，结论是**基线**。下一轮目标：登录优化（原生 bcrypt/worker threads）后跑 400/1000 VUs，并在生产规格 DB/多核机器上复测。

## 复现

```bash
# 1) 造数据（在 packages/server 下执行，读取该目录 .env）
cd packages/server
LT_CONFIRM=yes LT_PASSWORD='<压测统一密码>' LT_STUDENTS=1000 npx tsx ../../tests/load/seed-loadtest.ts

# 2) 预生成基准（1000 人）
npx tsx /tmp/loadtest-gen2.ts   # 或按报告方法直接调用 processPaperGeneration

# 3) 干净服务器（避免并行 WIP 干扰）
git worktree add --detach /tmp/p1c-load HEAD
ln -sfn "$PWD/../node_modules" /tmp/p1c-load/node_modules   # 按实际路径调整
ln -sfn "$PWD/packages/server/.env" /tmp/p1c-load/packages/server/.env
(cd /tmp/p1c-load/packages/server && PORT=3010 E2E_CAPTCHA_DEBUG=true npx tsx src/index.ts)
# 生产模式下的验证码答案只对回环 socket 放行（E2E_CAPTCHA_DEBUG），不可用于对外服务

# 4) k6
k6 run tests/load/exam-load.js \
  -e BASE_URL=http://localhost:3010 -e EXAM_ID=<考试UUID> \
  -e STUDENT_FROM=99000001 -e PASSWORD='<压测统一密码>' \
  -e SCENARIO=opening -e VUS=200

# 5) 清理（务必执行）
cd packages/server && LT_CONFIRM=yes npx tsx ../../tests/load/cleanup-loadtest.ts
```
